# M0/M2 기존 보호가 확인된 손절 강화 대기

## 발견과 원인

현재 목표 계약을 켠 실제 모델 재생에서 안쪽 SHORT의 부분익절 후 손절85860→85770 ADJUST가 선택됐다. 거래소 모형은 정상 응답을 반환했지만 새 손절은2초뒤 적용하도록 큐에 있었고, 즉시 조회에는 기존 Full Mark SL이 남았다. `_ensure_protection`은 `native_protection_not_confirmed`를 올렸고 runtime은 이를 `submission_unknown`으로 분류했다. 경제성 연구는 첫 기술 오류에서 중단하는 규칙에 따라27HTTP에서 봉인했다.

이후 보호 drain에서 취소 완료 대기도 발생했으나 최초원인이 아니다. 예외 추적으로 순서를 확인했고 초기 취소 원인 가설은 기각했다. 실패 연구의 모델 응답이나 결과는 수정하지 않았다. 별도 프로세스 재생은 감사행owner_pid 차이 때문에 전체 해시가 달랐으며, 이를 정확 재생 성공으로 보고하지 않는다. 그 메타데이터 문제는 별도 작업이다.

## 변경

`BrokerProtectionPending`은 정상 set_trading_stop 응답을 받은 단조 강화이며 다음 조건을 모두 만족할 때만 발생한다.

- 변경 전·직후 기존 Full Mark SL의 가격·방향·수량이 검증되고, 변경 전 보호는 이미 승인된 active 손절보다 후퇴하지 않았다.
- 두 조회 모두 legacy_fenced=False이고, 직후 노출은 양수이며 기존 관측보다 늘지 않았다.
- 새 목표 보호 수준은 아직 확인되지 않았다.

기존 `_write`가 응답 실패·모호한 전송을 먼저 거절한다. 새 예외도 실행을 즉시 중단한다. 따라서 새SL 확인 전에 뒤따르는 TP/추가주문을 실행하지 않는다. 진단 행은 기존 보호와 요청한 새 보호를 구분해 보존한다.

runtime은 **추가 진입이 없는 ADJUST**에서만 이 예외를 `awaiting_protection`으로 표시한다. intent는PENDING이다. 새손절 적용 완료·매매허가·정산완료를 뜻하지 않는다. 추가진입이 있는ADJUST나 다른 행동은 기존 일반미확정 분류를 유지한다. 이후 기존 보호 점검과 정확조회가 새보호를 확인한뒤 기존 복구경로가 다음단계를진행한다. 위험 예산·레버리지·목표·기존 취소 ACK 분류는 변경하지 않는다.

## 검증과 운영 범위

원 코드에서 정상 지연의 예상분류 회귀가 실패하는 것을 먼저 확인했다. 정상 지연, 전송실패, 거절응답, 이전/이후native보호 소실, 보호수량 부족, LastPrice 트리거, 손절 후퇴, 노출 증가를 검사한다. LONG/SHORT 모두 실제 격리 런타임에서 새보호 적용뒤에만 대체TP가 생성되는지와 저장/재생 결과 일치를 확인한다. 추가진입이 있는경우와 보호미확인은계속실패한다.

이 변화는 확인되지 않은 새 보호를 성공으로 간주하지 않는다. Bybit공식 응답에는 보호주문식별필드가 없으므로 retCode0만으로 적용을 인정할 수 없으며 기존보호 관측을 별도로 확인한다. [공식 Set Trading Stop 문서](https://bybit-exchange.github.io/docs/v5/position/trading-stop).

실제 모델 호출 없이 회귀를 검사하며, 봉인된27회 연구를 재개하지 않는다. CI·배포·첫 정기 관측은 구현/테스트와 별도다. 기존 과거 미정산2건 및 원24시간 복구 구간의 실패 기록은 유지한다.
