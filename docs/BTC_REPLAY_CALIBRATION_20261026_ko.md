# M2 실행 재생 보정: 최초 3건

2026-10-26. 사용자의 표본 백테스트 요청에 따라 먼저 실제 종료 거래와 도구를 대조했다.
15분봉 제외 배포 이후 진입한 확정 종료 거래를 시간순으로 3건 고정했다. 결과를 보고 고르지 않았다.
원 거래소 체결로 원장 손익·수수료·잔량을 독립 재계산한 3건은 모두 일치했다. 이는 가격 경로 예측 검증과 다르다.

## 입력과 사전 기준

- 실제 주문 요청/응답 33쌍과 독립 Bybit 공개 1분 Last/Mark 각 443개를 연결했다.
- 실제 관측된 요청→응답 간격을 지연 가정으로 사용했다. 이는 서버의 정확한 주문 접수·체결 시각이 아니다.
- 기존 ScenarioExchange/Driver의 OHLC·OLHC, 수수료·5bp 슬리피지·1bp 스프레드·유동성 가정을 유지했다.
- 잔량/역할별 수량 일치, 순손익 오차 0.01 USDT 이하, 수수료 오차 0.000001 USDT 이하를 사전 기준으로 삼았다.
- 실제 주문 변경 일정을 입력으로 사용한 실행 모형 진단이다. 후보 전략의 반사실 보유 판단 재생이 아니다.

## 발견한 결함과 최소 수리

기존 모형은 이미 쉬고 있는 maker 지정가도 taker의 반대 호가까지 넘어야 체결하도록 했다.
가격이 실제 지정가를 통과해도 스프레드만큼 더 움직이지 않으면 거래를 놓쳐 두 사례의 첫 익절이 누락됐다.
rested limit만 Last 거래 가격과 비교하고, 신규 시장성 limit/Market·가격 변경 직후에는 기존 quote와
슬리피지 적용을 유지한다. 기존 수량 한도·지연·수수료·손절 순서는 그대로다.

maker가 호가에 유동성을 제공하고 taker가 이를 가져간다는 구분은
[Bybit 공식 설명](https://www.bybit.com/en/help-center/article/Comparison-Between-Maker-Orders-and-Taker-Orders)을 확인했다.
Last 기반 maker 판정은 이 모형의 가정이며 실제 호가 대기열이나 체결 확률을 입증하지 않는다.

LONG/SHORT의 스프레드 안쪽 trade-through 미체결을 변경 전 2개 실패로 재현했다.
수정 후 직접 소비 경로 포함 95개 테스트를 통과했다. 운영 주문 코드는 변경하지 않는다.
