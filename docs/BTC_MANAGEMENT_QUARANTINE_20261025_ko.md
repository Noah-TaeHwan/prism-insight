# M0: 미확정 부분손절의 제한적 보유 관리 복구

## 사용자 승인과 완료 범위

2026-10-25 사용자는 미확정 이력·신규진입 차단을 유지하면서 기존 보유분의 WAIT/명시적 EXIT 판단을 재개하는 수리를 승인하고, 복구 후 기존 개선 작업을 이어가도록 요청했다. 데모만 대상이다. 원 요청 결과를 만들어내거나 새 진입을 자동 허용하는 승인은 아니다.

복구 완료는 새 시세 기반의 제한적 보유 판단, 원 계약 실패 시 EXIT 권한, 별도 native Full SL 보호가 연결되는 것으로 검증한다. 실제 선택·체결이 없으면 해당 경로의 자연 관측은 미확인이다. 원 UNKNOWN의 진실 규명·전체 정산·신규 매매 완전 재개는 추가 거래소 근거가 필요하며 이 수리만으로 완료 선언하지 않는다.

## 변경 전에 고정한 범위

1. 기존 broker_evidence에 사고 전용 append-only 관리자 승인 기록을 보존한다. 정책 버전·사용자 승인 근거·계정·endpoint·원 시나리오/계약·대상 UNKNOWN child/요청 해시·허용 행동 WAIT/EXIT·승인 시각/기한·무결성 해시를 결박한다. 해시는 인증 수단이나 거래소 증거가 아니다.
2. 현재 사고는 UNKNOWN child 하나가 전역 대조를 막아 기존 OPEN/ADJUST/REDUCE intent 세 개가 PENDING이다. 승인 당시의 선행 intent ID와 원 payload 해시를 고정하고, 원 상태를 바꾸지 않는다. 다른 UNKNOWN·미체결 진입·새 미해결 EXIT가 있으면 예외를 허용하지 않는다. native Full SL의 LIVE 상태는 별도로 검증한다.
3. broker 문맥에서 매번 원 요청·계정·현재 잔량/방향·신선한 Full SL·승인 범위를 재검증한다. UNKNOWN, 미확정 회계, 원 계약/계획은 그대로다. 새 위험은 차단한다.
4. runtime 초기 PENDING 검사·원 계약 FAILED→EXIT·모델 후 fresh 검사·commit 직전에서 같은 제한 권한을 확인한다. 모델 문맥/schema/호스트 검증 모두 WAIT/EXIT만 허용한다. ADJUST/REDUCE/OPEN·renewal·임의 취소 배열은 금지한다. 승인 철회·변조·조건 변화는 stale/blocked다.
5. 격리 EXIT는 지정 UNKNOWN을 재제출·재취소하지 않는다. 나머지 주문은 기존 정확한 대조·취소 경로를 사용한다. 최신 잔량 이하의 reduceOnly EXIT를 기존 durable-before-POST 및 고정 ID로 한 번만 제출한다. native Full SL은 먼저 취소하지 않는다.
6. EXIT 응답 유실·재시작·동시 부분손절/TP 체결을 검증한다. 이미 생성된 EXIT child는 조회만 하며 재전송하지 않는다. 원 UNKNOWN과 원 intent·정산을 임의 완료 처리하지 않는다.
7. 포지션이 0이거나 승인이 만료·철회돼도 원 UNKNOWN이 해소되지 않으면 신규 진입은 계속 차단한다. 경보는 ‘정상 복구’가 아니라 제한 관리 여부와 미확정 정산을 구분한다.

## 검증 기준

- 정상 WAIT/EXIT·원 계약 FAILED 경로와 승인 없는 기존 차단을 실제 runtime/broker 가짜 거래소 모듈로 먼저 재현한다.
- 계정·시나리오·계약·요청·선행 intent 해시 변조, 승인 철회/만료, 다른 UNKNOWN, 미체결 entry, 미해결 EXIT, 오래된 계정/시세/보호는 모두 거부한다.
- 모델 DRAFT 후 승인 변경, final commit 직전 변경, 보호 점검 경합, EXIT 중 잠복 stop 체결, POST ACK 유실/재시작을 검증한다.
- 원 child/intent/정산 미확정 보존과 지정 UNKNOWN의 재취소 0회, EXIT POST 최대 1회, 반대 노출·전체 손절 공백 없음이 필수다.
- 프로비넌스·schema·입력 크기·기존 회귀·정확한 최종 전체 테스트·CI·독립 검토 후 별도 M0 PR로 배포한다. 활성화는 사용자 승인과 최신 계정에 결박된 관리자 절차로 한다. 시험 주문·강제 청산·수동 tick은 하지 않는다.

## 분리할 작업

진입 선택 후보 Draft PR #1115는 이 변경과 묶지 않는다. 손익비·수익성 개선 주장은 없고 10배·위험 예산·15분봉 제외·기존 시간봉 우선순위는 불변이다. 이미 수행한 단일 취소의 서버 marker를 삭제하거나 다른 이름으로 반복하지 않는다.

## 구현·검증 결과와 해제 절차

- 승인 기록, runtime/schema/호스트 검증, fresh receipt, 단일 HTTP EXIT, 별도 관리 상태 경보를 연결했다. 새 의존성·모델 배치·cron은 추가하지 않았다.
- 실제 runtime/broker/검산·선택 경로의 LONG/SHORT 가짜 거래소 통합 37개가 통과했다. 보호 유지·원 UNKNOWN 보존·응답 유실 뒤 조회만 수행·원 계약 FAILED의 모델 없는 EXIT·권한 철회 경합을 포함한다.
- 최종 관련 520개가 실제 SDK 환경에서 통과했으며 네트워크 시도 0회다. 전역 foreign LIVE 차단은 기존에 있었고, NULL 상태/시나리오 및 child 없는 foreign 미완료 intent 경계만 추가 보강했다. 과거 TERMINAL 이력은 허용한다.
- 별도 health/provenance 관련 175개가 통과했다. 신규 모듈은 검토·판단·실행 출처에 모두 결박했고, 소스 목록 고정값을 26→27로 갱신했다. 최종 전체 테스트·CI·배포·정기 실행은 아직 별도 단계다.
- 원 UNKNOWN이 실제 정확한 TERMINAL 근거로 해소돼도 유효한 관리 승인을 자동 은퇴시키지 않는다. `quarantine_release_required`로 새 모델/intent 생성을 막고, 관리자 `revoke` 후 기존 검증 경로로 돌아간다. 이것은 source 삭제·빈 조회를 해소로 인정하는 절차가 아니다.
- 이미 committed EXIT가 있으나 child가 없는 상태에서 승인 만료·철회가 발생하면 새 POST는 금지되고 그 intent는 보류된다. 이 상태의 자동 해소를 보장하지 않는다. 해제 후 일반 관리 재개 검증은 추가 미해결 EXIT가 없는 경우를 대상으로 한다.
- 잔량이 0이어도 원 UNKNOWN이 남으면 `flat_quarantined_unsettled`로 표시한다. 해제 대기·무포지션 미정산을 처리 오류 폭주로 합산하지 않되, 별도 경보와 읽기 전용 시세 관측을 유지한다.

이 문서는 코드·오프라인 검증 상태다. 실제 보호 청산이나 완전 정산·신규 매매 재개를 증명하지 않는다.
