# M0/M2 소스 검증의 반복 컴파일 비용

## 변경과 안전 경계

`scenario_provenance._loaded_parity`는 동일 소스를 매번 Python code object와 AST로 다시 만들었다. 기존 서버 계측에서 binding3회1.28초 중 이 변환의 compile 비용은 약0.99초였다. 최근9개 운영 실패는 최종75초 검증 제한이었지만, 전체 응답 후 처리 약8초를 이 비용만으로 설명하지는 않는다.

전체 소스 문자열을 키로 삼는 표준 lru_cache를 비교용 compile/parse에만 적용한다. 각각 최대64항목이다. 소스 파일 읽기·해시, 실제 로드된 함수 코드와 현재 설정 값의 비교, VERIFIED/MIXED/UNKNOWN 판정은 매번 수행한다. 파일명만으로 캐시하거나 판정 결과를 재사용하지 않는다. TTL·75초 제한·계좌/가격 신선도·모델·프롬프트·위험 기준은 변경하지 않는다.

## 검증

변경 전에 따뜻해진 비교 자료에서 함수 변조·가변 설정 변조·동일 모듈명의 소스 변경·모듈 누락이 탐지되는 검사를 고정했다. 이후 소스 함수 본문 자체가 달라지는 반례도 확인했다. 직접 관련32검사, 추가 본문 반례를 포함한5개 경계 검사, 런타임 경제성/목표/PID재생48검사가 통과했다. 하위 프로세스가 live 패키지를 찾도록 테스트의 PYTHONPATH를 명시했다. 전체는 PR CI에서 확인한다.

같은 로컬 환경에서 초회1회+반복6회, 유료 모델·거래소·DB 호출 없이 비교했다. 반복 binding 중앙값은0.154680초→0.009774초, 호출당 약0.144906초 감소했다. 각 실행 안의 반복 binding은 같았고, 전후에는 변경된 소스 파일 자체의 해시를 제외한 binding이 일치했다.

이는 로컬 순수 함수 계측이다. 운영 서버 전체 판단이15.8배 빨라졌다는 뜻도, 시간초과가 모두 사라졌다는 뜻도 아니다. 운영 적용 후 실제 정기 판단의 시간과 실패를 별도로 확인해야 한다.

근거: `tasks/btc-parity-source-cache-20261027/`의 사전검토·before/after/comparison.json. 모델호출0·주문0이며 전략 수익성 입증과는 별도다.
