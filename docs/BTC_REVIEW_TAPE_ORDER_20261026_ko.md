# M2 저장된 판단 기록의 정확 재생 수리

운영 slot5976695 기록을 읽어 다시 검증할 때 첫 차이는 `request.user_prompt`의 `contract_context.recovery.changed_evidence.key_order[0]`였다. 입력 압축은 변경 근거의 삽입 순서와 그 순서의 해시를 기록한다. 반면 runtime의 SQLite 저장과 EconomicTape의 파일 저장은 `sort_keys=True`로 모든 객체 키를 정렬했다. 값이 같아도 다시 구성한 요청 문자열은 원 요청과 달라져 정확 재생이 실패했다. 인메모리 검산 성공을 디스크에서 다시 읽은 재생 성공으로 간주하면 안 된다.

두 저장 지점에서 키 정렬만 제거해 원 순서를 보존한다. 모델 호출·프롬프트·위험 한도·75초 제한·해시 알고리즘·엄격한 요청/결과 비교는 바꾸지 않는다. 기존 파일이나 운영 DB 기록은 소급 수정하지 않는다. 이미 순서를 잃은 과거 기록을 통과했다고 재분류하지 않는다.

회귀 검증은 100개 변경 근거를 의도적으로 역순으로 넣고 실제 runtime의 1회 WAIT·2회 후보 선택을 실행한다. SQLite와 경제성 재생 파일에서 다시 읽은 기록을 정확 재생한다. 수정 전 4개 사례 모두 실패, 수정 후 모두 통과했다. 다시 정렬해 순서를 잃게 만든 기록은 계속 거절하며 재생은 추가 모델 호출이나 주문을 만들지 않는다.

관련 runtime·리뷰 테이프·경제성 재생·비교 테스트 142개가 통과했다. 기존 snapshot의 NumPy timedelta 사용에 대한 deprecation 경고는 범위 밖으로 남긴다. CI·배포·새 정기 판단의 저장 후 정확 재생은 별도 단계다. 이는 M2 판단 기록의 재현 수리이며, 실제 체결 가격·순손익 재현이나 M5 수익 개선 입증을 뜻하지 않는다.
