# BTC 가정 평가 상태 비교 수리

## 범위와 원인

M0/M3 실행 안전성 수리다. 2026-10-22 감사의 네 DRAFT(5975486/5975490/5975497/5975499)는
계약 ID와 WEAKENING 상태가 같고 설명의 `0회입니다.`/`0회.` 표현만 달랐지만
전체 assessment 사전의 동일성 검사 때문에 SELECT에 도달하지 못했다.
설명 문구 차이를 계약 상태 충돌로 취급한 것이 원인이다. 당시 실제 모델의
후속 선택·체결 결과는 존재하지 않으며 오프라인 후속 선택으로 소급하지 않는다.

## 수리 및 보존 경계

- 비교용 복사본에서 `reason`만 제외한다. 원본 설명·원응답·계산 receipt·해시는 수정하지 않는다.
- 계약 ID와 상태 등 나머지 모든 키는 비교한다. 임의 필드 무시·공백 정규화·설명 복사는 없다.
- schema 및 metadata 검증은 그대로다. 누락·추가 키·빈/공백/비문자/과도하게 긴 설명과
  잘못된 계약 ID·상태, null/객체 불일치는 여전히 거부한다.
- FAILED의 WAIT는 선택 불가능한 템플릿이며 유효한 EXIT 후보만 허용한다.
  가정 실패 확정 조건·전량 EXIT·native SL·위험·수량·주문 권한은 바꾸지 않는다.
- DRAFT 동적 지침과 response_contract 지침을 같은 상태 비교 규칙으로 맞춘다.

## 검증 기준

동일 계약·상태에서 설명만 다른 LONG/SHORT×네 상태를 먼저 기존 코드에서 실패 재현한다.
수정 후 원문 두 개가 각각 보존되는지, 선택 및 exact guard replay가 되는지 확인한다.
별도로 잘못된 assessment·상태 충돌·FAILED 비EXIT·해시/원문 변조 반례를 유지한다.
실제 네 보관 입력의 오프라인 점검, 전체 검사·CI·배포·첫 자연 판단은 각각 구분한다.
추가 모델 호출이나 시험 주문은 필요하지 않으며 수익성 개선 주장은 하지 않는다.
