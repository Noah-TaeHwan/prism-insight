# M0 조회 공백 이후 명시적 복구

2026-10-26 15:30:17 KST에 최초 incident HALT가 기록됐으며, 사유는 `HISTORICAL_MONITOR_OR_COVERAGE_GAP`였다. 당시 상세 예외는 기록되지 않아 네트워크 오류인지 시간 초과인지 소급 확정하지 않는다. 15:31부터 두 사건의 금융 cursor가 중단 전 cursor를 이어 다시 갱신됐으나, 기존 코드는 HALT가 한 번이라도 있으면 영구 차단했고 복구 경로가 없었다. 새 체결로 단정할 증거는 없다.

복구는 정기 runner가 자동으로 수행하지 않는다. 운영자가 검토한 HALT 집합의 정확한 해시를 지정하고 `release_monitor_gap`을 호출하면 기존 mutex 안에서 실제 금융·계좌를 다시 조회한다. 과거 스냅샷 불변, 금융 조회 범위 완전성, 모든 계좌 범위 무포지션·무주문, 신규 미확정 의도 없음, 기존 demo 신원과 위험 권한, 관측 10초 이내 조건이 모두 맞아야 복구 영수증을 추가한다. 과거 HALT나 UNKNOWN은 삭제하지 않는다.

체결·수수료 변경을 담은 HALT는 이 경로로 해제하지 않는다. 복구 후 같은 조회 공백이 재발해도 새 HALT를 기록하고 차단한다. 영수증 변조·새 HALT·과거 기록 변경은 차단하며, healthcheck도 같은 유효 차단 상태를 사용한다. 향후 오류는 예외 종류와 허용된 내부 사유 코드만 기록한다. API 원문·인증 정보는 남기지 않는다.

위험 한도, 10초 기준, 자동 재진입, 수익성 정책은 바꾸지 않는다. 이번 경보로 기존 24시간 무경보 구간은 미충족이며 삭제하거나 성공으로 재분류하지 않는다. 복구 이후 새 관측 구간은 별도로 기록한다. 코드·테스트·CI·배포·실제 복구·정기 판단 재개를 구분한다.

로컬 검증: 사건 격리·entry epoch·healthcheck 관련 232개 통과, 로컬 pybit 미설치에 따른 기존 키 만료 테스트 4개 제외. 최종 변경 후 복구 경계 9개를 다시 검사해 모두 통과했다. 운영 복구와 첫 판단은 아직 미확인이다.
