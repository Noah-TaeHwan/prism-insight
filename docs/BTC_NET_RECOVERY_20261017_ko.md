# BTC 비용 후 순손익 기반 단계 회복

## 도입 검토 6항목 (M0/M1/M3/M4, M5 미입증)

1. **변경 유형·기준선:** 사용자 승인 경제 정책 변경이다. 자동 회복 policy_version=2는
   유지하고 promotion_rule_version=3을 구분한다. 이전 규칙의 연속성·승수 중심 체크포인트를
   최근 최대 6건의 해당 단계 확정 체결·정산 순손익 창으로 바꾼다.
2. **가설·반증:** 작은 손실 하나가 누적 순이익을 모두 무효화하지 않도록 하고 실제 비용 후
   회복을 본다. 더 빠른 승격이 후속 손실·낙폭을 키우면 유리한 변경이라는 가설은 지지되지
   않는다. 6건·양수 2건은 초기 실무값이지 최적값이나 통계적 수익성 증거가 아니다.
3. **연결 궁합:** `scenario_recovery.py`의 정산 증거/허용 단계 → runtime 입력 →
   `scenario_llm.py` 공유 프롬프트 → 후보/최종 선택 → 최신 위험 검사 → accepted OPEN의
   permit 확정 순서다. LLM은 시장 방향·가격·배분을 판단하되 승격 계산·요청·확정은 하지 않는다.
   같은 창에서 양수 정산 2건 이상, 비용 후 합계 양수, 단계 예산 이내의 확정거래 낙폭을 모두
   충족하면 다음 새 OPEN에 한 단계 상향을 제안한다. 단계 1/2는 창의 순손익 음수 또는
   낙폭 초과 시 하향하며 단계 0의 손실도 최근 6건에 남긴다. 단계 변경 때만 창을 초기화하고
   전체 정산 이력은 보존한다. 무체결은 제외하고 순손익 0인 체결 정산은 창에는 포함하되
   양수 건수로 세지 않는다. TP/SL·10배·모델·기존 0.5/1/2% 한도는 바꾸지 않는다.
4. **검증:** 수익-작은 손실-수익, 누적 음수·낙폭 초과, 경계값, 중복 정산·손상 기록·누락
   증거·무체결·정산 0, 활성 구규칙과 flat 전환을 반례로 검증한다. LONG/SHORT와 보유/무포지션의
   실제 후보·선택 조립에서 권한 분리 문구도 확인한다. 독립 holdout·표본 검정력·수익성 비교는
   수행하지 않았으며 테스트 성공을 성과 개선으로 간주하지 않는다.
5. **유지·중단·복귀:** 최초 자연 판단과 실제 정산 시 규칙 버전·창·허용 단계를 원본 ID로
   대조한다. 중복 집계·누락 덮어쓰기·활성 한도 변경은 안전 결함으로 다룬다. 최근 손익만으로
   자동 정책 왕복은 하지 않는다. 통계적 관측 종료 시점은 미설정이고 별도 LLM 배치를 추가하지 않는다.
6. **현재 결론:** 승인된 데모 변경의 구현/검증 대상이다. CI·배포·최초 자연 실행·후속 정산
   관측은 별도 증거로 보고한다. 수익 개선은 미입증이며 실자금 승인은 포함되지 않는다.

## 이행 경계

- 활성 rule 2 시나리오는 정확히 정산될 때까지 기존 규칙·permit·위험예산을 유지한다.
- flat OBSERVING 전환은 옛 합계와 근거를 감사 이력으로 남기되, 옛 승수나 임의의 거래 ID를
  새 창에 채워 넣지 않는다. 새 규칙 이후의 확인된 정산부터 쌓는다.
- 각 창 행은 실제 scenario_id·settlement_hash·net_pnl·settled_at으로 연결한다.
  코드의 현재 promotion_rule_version 및 offered stage가 권한 기준이다.
- 확정거래 낙폭은 장중·전체 계좌 낙폭과 다르며 기존 일 손실/보호/미확정 실행 차단을 대체하지 않는다.
- 부분익절이나 미실현 이익으로 승격하지 않고, 승격 표본을 채우려고 거래하지 않는다.

## 프롬프트 모순 정리

기존의 “손실이면 단계 하향” 문장을 rule 3에도 무조건 적용하면 작은 손실을 허용하는
새 창 규칙과 모순된다. 현재 호스트 규칙에 따르도록 바꾸고, 구규칙은 활성 거래 종료까지
보존한다고 명시한다. 후보와 선택 단계 모두 동일 SYSTEM을 사용하며 주문 권한은 여전히 없다.
